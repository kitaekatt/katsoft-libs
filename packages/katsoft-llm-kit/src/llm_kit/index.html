The llm_kit core library: the unified completion protocol across OpenAI-compatible HTTP, Claude CLI, Codex CLI, and OpenCode CLI backends, with dispatch routing, the front-door API, the graph viewer, the CLI, job and run management, and the deployment-mode runtime

This is the core of the llm-kit package. One completion protocol is implemented by four transport backends: OpenAI-compatible HTTP, the Claude CLI, the Codex CLI, and the OpenCode CLI. A dispatch layer selects and paces backends by configuration; a front-door API exposes the package to callers. A CLI wraps the same path for terminal use. Beside the completion path: job and run management, a graph viewer, schema and storage, and a deployment-mode runtime that keeps source and installed copies from colliding.

Where to start

Open packages/katsoft-llm-kit/src/llm_kit/adapters/backends.py to see how the HTTP and Claude CLI transports implement the shared protocol. The protocol types in the completion directory one level up define the interface both sides speak.

Routes

  • Complete a prompt (CLI transport)
    1. dispatch selects the backend by configuration
    2. packages/katsoft-llm-kit/src/llm_kit/adapters/backends.py builds argv and spawns the CLI
    3. packages/katsoft-llm-kit/src/llm_kit/adapters/claude_runner.py drains both pipes with a per-call timeout and hard-stop kill
    4. the result is parsed into the shared LLMResponse type
  • Run an agent session
    1. packages/katsoft-llm-kit/src/llm_kit/adapters/claude_session.py spawns claude -p with stream-json I/O
    2. a stdin driver writes the prompt and forwards mailbox messages
    3. packages/katsoft-llm-kit/src/llm_kit/adapters/claude_stream.py parses each stdout line into an event verdict
    4. the control loop applies quiescence, timeout, and stop rules
  • Add a new transport adapter
    1. implement the LLMBackend protocol from the completion layer
    2. packages/katsoft-llm-kit/src/llm_kit/adapters/capabilities.py add a capability record beside the existing adapter records
    3. register the backend in the dispatch factory

Deployment and runtime

Three files at the package root. packages/katsoft-llm-kit/src/llm_kit/_deployment.py declares whether this copy is source, legacy, or an installed wheel. packages/katsoft-llm-kit/src/llm_kit/_runtime.py reads that marker, verifies the layout, routes three shared contracts through katsoft-contracts, and decides once per process whether the plugin marketplace's bootstrap library is importable. packages/katsoft-llm-kit/src/llm_kit/bootstrap_guard.py detects whether the bootstrap plugin has provisioned this plugin and re-execs the process under the provisioned venv when needed.

Completion protocol and dispatch

The completion directory defines the shared interface: response types, the halt taxonomy, capability records, the output-contract pipeline, session types, and prompt folding. The dispatch directory holds backend factories, pacing policy, and reachability probes that a pipeline or the front door calls to obtain a completion.

Backend adapters

  • packages/katsoft-llm-kit/src/llm_kit/adapters/backends.py -- OpenAI-compatible HTTP and Claude CLI backends; thread-safe client build, cost reporting, and effort planning
  • packages/katsoft-llm-kit/src/llm_kit/adapters/codex_backend.py -- codex exec transport; result arrives in a file, usage rides on stdout as JSONL events
  • packages/katsoft-llm-kit/src/llm_kit/adapters/harness_adapters.py -- command-line adapters for Codex and OpenCode harness entries; builds argv, never runs the process
  • packages/katsoft-llm-kit/src/llm_kit/adapters/capabilities.py -- filled capability records; every value derived from adapter code and asserted by seam tests
  • packages/katsoft-llm-kit/src/llm_kit/adapters/claude_session.py -- stream-json agent session with process lifecycle, mailbox forwarding, and quiescence control
  • packages/katsoft-llm-kit/src/llm_kit/adapters/claude_stream.py -- stream-json line parsing and the event verdict shared by relay and session
  • packages/katsoft-llm-kit/src/llm_kit/adapters/claude_runner.py -- shared prompt-on-stdin subprocess runner with UTF-8 pipes and hard-stop kill
  • packages/katsoft-llm-kit/src/llm_kit/adapters/claude_command.py -- Claude executable selection, batch-shim detection, and system-prompt file spillover
  • packages/katsoft-llm-kit/src/llm_kit/adapters/codex_command.py -- Codex CLI detection, argv construction, and absolute-path enforcement
  • packages/katsoft-llm-kit/src/llm_kit/adapters/claude_env.py -- the single definition of the Claude child environment across all spawn paths
  • packages/katsoft-llm-kit/src/llm_kit/adapters/client.py -- lazy OpenAI SDK client pointed at a named endpoint; keyless endpoints pass a placeholder
  • packages/katsoft-llm-kit/src/llm_kit/adapters/account.py -- OpenRouter account validation and non-raising endpoint reachability probes
  • packages/katsoft-llm-kit/src/llm_kit/adapters/endpoint_profile.py -- per-endpoint facts that specialize a family's capability record for effort delivery
  • packages/katsoft-llm-kit/src/llm_kit/adapters/_cmd_shell.py -- the one list of cmd.exe metacharacters refused on both Claude and Codex spawn paths
  • packages/katsoft-llm-kit/src/llm_kit/adapters/_swapper_process.py -- local process inspection and identity-bound signalling; packages/katsoft-llm-kit/src/llm_kit/adapters/_swapper_errors.py carries the shared error vocabulary

Front-door, CLI, and execution

The front-door directory exposes the package's public API to callers. The CLI directory provides the terminal entry point. The execution directory carries support for supervised processes and worker launches that the pipeline and graph layers invoke.

Graph viewer

The graph directory renders pipeline state as an interactive viewer. It contains command definitions, operation definitions, a render layer with static assets and vendored JavaScript, and the viewer shell with its own static directory. Open it when you need to inspect or extend how pipeline runs are visualized.

Jobs, runs, and schemas

Job schemas define the multi-step work contract and its validation. Run management tracks individual executions and comparison scoring. The schema directory holds format definitions with a formats subdirectory, storage persists state, and scaffold generates project boilerplate.
